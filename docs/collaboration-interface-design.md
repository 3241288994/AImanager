# 轻量协作：Skill、CLI、配方的接口定稿

日期：2026-10-21  
状态：设计定稿，首版接口已实现为 `ai-collab 0.2.0`。本文保留设计依据与取舍，实际支持范围以[使用说明](ai-collaboration.md)为准。

## 1. 总体决定

一份中立的协作 skill，配合已有 `ai-collab`，再按需读取少量 Markdown 配方。

- 主控负责判断、材料选择、结果整合。
- CLI 负责调用、目录和会话、后台任务与结果。
- 原生 harness 自己负责工具循环、编辑、命令和内部上下文。
- 配方提供领域无关的协作形态；具体领域知识复用当前主控已有能力。
- 不新增中心数据库、调度平台、消息总线或流程语言。

首版已有 `claude-code`、`gemini-web` 与 `codex-cli` 适配器。Claude 主控可通过同一工具委派给 Codex；“任意主控”要求入口具备调用 CLI 或薄 MCP 的能力，不能仅靠改名成立。

## 2. 通用 Skill

### 结构

```text
skills/multi-model-collaboration/
  SKILL.md
  references/cli.md
  recipes/review.md
  recipes/plan-execute.md
  recipes/research.md
  recipes/writing.md
```

保留现有 skill 名称兼容安装和触发。一个源文件，按目标 harness 实际支持的方式注册或安装；不假定所有宿主都支持同样的路径、软链接或元数据。没有 skill 机制的入口可以加载同一份简短使用说明。

### 触发说明草案

> 用户要求与已配置模型协作，或请求将分析、复核、执行委派给另一参与者时使用。模型名单独出现表示为当前任务指定协作者；比较模型或在文档中提及名字不触发调用。没有当前任务时先明确工作目标。

### 正文只保留这些规则

1. 当前主控负责最终交付，不限定为 Codex。
2. 解析用户指定名字，保持模型、渠道和版本；按现有配置使用账号。
3. 从当前任务识别目标、必要材料、工作目录、操作范围与期望结果；用户已提供的内容不重复询问。
4. 按实际能力选择文本、只读或执行；任务需要操作时才申请对应调用，不把角色名称当权限。
5. 默认委派一个有价值的子任务；只有可独立推进的工作才并行。
6. 独立复核先给原始材料；补充讨论再提供具体分歧。材料不足时补证，不要求模型猜。
7. 用 `reply` 延续同一协作者，用新 `run` 与必要材料接力；不把完整主控对话及全部 skills 注入每个协作者。
8. 返回结论、交付文件、实际检查与未解决问题；主控按任务核实并决定采纳。
9. 长调用使用后台 job，等待有上限并向用户更新进展；失败不静默换模型、不重复执行有副作用的任务。
10. 得到可用结果、缺少必要条件或达到约定范围时收尾，不重复征求同意。

正文以简短为目标，不用固定行数约束质量。完整参数、模型升级与远程调用说明放入 `references/cli.md`；配方按需读取，不每次加载全部文件。

主控可以提取现有论文、实验、开发 skill 的相关检查点。协作者在受支持且经过配置的执行环境中使用自己的项目说明和必要工具，不要求复制主控的整个个人环境。

## 3. CLI：兼容现有命令，新增一个 reply

### 使用面

| 接口 | 状态及用途 |
| --- | --- |
| `resolve`、`doctor`、`models`、`alias` | 已有，继续负责配置与能力发现；doctor 不等于推理成功 |
| `run` | 已有，创建一次调用；扩展访问方式和可选主机 |
| `reply JOB` | 新增，向同一对话补充信息并创建下一轮 job |
| `status`、`wait`、`result`、`cancel` | 已有，继续管理后台调用 |
| `jobs` | 已有，新增按工作区过滤以便接手 |
| `run --after JOB` | 已有，只附带指定成功 job 的结果文本，仍是新调用 |

选择 `reply` 而不是 `run --continue`：续接继承已有模型、账号、目录和权限，单独命令可以直接拒绝冲突参数，使用者也更容易区分“继续聊”与“请另一位协作者接手”。

### 访问方式

新增 `--access text|read|exec`，它描述运行范围，不描述模型角色。

| 值 | 行为 |
| --- | --- |
| `text` | 只提供显式输入材料，不授予本机文件或命令工具 |
| `read` | 原生协作者可读取指定目录，不能修改或执行任务命令 |
| `exec` | 使用已配置并核实的原生执行方式，允许任务范围内的编辑和命令 |

兼容默认：不指定工作区时为 text；已有 `--workspace` 用法仍为 read；exec 必须显式选择。不支持所需能力时返回明确错误，不静默退回文本回答。

API 当前仅支持 text；以后可通过适配器增加工具或其他输入支持，不在核心中永久限制为无工具。原生特性通过适配器明确支持的选项扩展，不开放任意 CLI 参数穿透。

### 工作目录

- `--workspace` 是协作者实际访问的目标；read 的第一个根目录作为实际 cwd，其他根目录只用于明确的额外读取。
- exec 只接受一个执行工作区；相对路径以它为基准。
- 原有 `--cwd` 继续记录发起位置，避免改变既有语义。新增 `effectiveCwd` 记录实际子进程目录。
- text 使用受控任务目录，不因发起位置而意外加载某个项目。
- 工作目录与配置加载方式共同决定运行环境，实施时需要验证只读模式切换 cwd 后仍保持原有边界。

这是一项有意的 cwd 行为修正，不是完全无变化的兼容升级：旧参数、默认访问等级保留，项目说明加载可能变化。必须在 doctor 能力说明和发布说明中明确；按 provider 验证项目指令加载策略，不依赖 cwd 或 `--setting-sources` 的偶然副作用。配置与能力验证前保持当前实际行为。

### 提议用法：以下新参数和 reply 尚不可运行

```bash
# 请协作者查看项目
ai-collab run --model opus5.5 --workspace /project \
  --prompt-file task.txt

# 在主控事先准备的工作区内执行
ai-collab run --model opus5.5 --access exec \
  --workspace /project-task --prompt-file task.txt

# 继续同一个参与者的会话
ai-collab reply JOB_ID --prompt-file followup.txt

# 给另一位参与者相关材料，开始新调用
ai-collab run --model gemini4 --file selected-results.txt \
  --prompt-file review-task.txt
```

用户不必手写这些命令；主控根据自然语言调用。`--after` 不自动附带源文件、整段历史或远端路径内容。需要缩短历史时，用新的摘要文件开启新调用，不能同时把过长原文重新附上。

## 4. 会话与轻量状态

每轮独立 job，沿用现有文件存储，新增 `parentJobId` 与 `conversationId` 关联轮次。不覆盖历史结果。

`reply` 只接受新提示、材料和调用时限等；继承模型、提供方、原生账号 profile、主机、工作区、实际 cwd、访问方式及执行配置。不得通过续接升级权限。

- 原生 CLI：保存并续接明确的 session ID，不使用“最近会话”猜测。
- API：根据必要显式历史构造 messages，标明是 API 历史续接。
- 原生账号绑定固定；API 账号池固定端点、池配置与凭据引用，不能承诺池背后的实际账号固定。有实际服务账号返回时记录。
- 仅允许从会话最新一轮续接；提交与会话占用检查必须原子完成，不能两个调用同时操作同一会话。
- 最新一轮必须为 succeeded；原生调用还须确认已持久化且有可用 session ID，API 须保存所需历史。旧版不持久化的 job 即使返回过 session ID，也属于不可续接。
- failed、cancelled、timed_out、interrupted 或失联的任务首版不自动续接；返回 `not_resumable`，先核对实际进程与副作用，不能隐式重跑。
- 无法恢复、身份/目录不兼容或原始 job 不可续接时明确报错。主控可显式新建调用并交接材料，不自动重开。
- 历史超过输入预算时提示整理材料；不无界回放，不偷偷丢弃中间消息。

会话文件保存在对应原生账号 profile 中；API 历史保存在工具自己的 job 数据中。凭据仍来自已有管理方式，不复制进提示或成果。

最少新增记录为：会话关联、有效 cwd、访问/执行方式、原生会话 ID、远端主机引用。沿用已有配置、状态、输入、结果和有限原始日志；API 需要时保存 messages，明确交付物可放在 artifacts 目录。

结果仍以自然语言 `text` 为主，不要求模型输出复杂 JSON。工具返回确定的模型、主机、状态、会话和文件元数据；“检查过什么”仍是执行报告，主控据日志或实际操作核对。

调用成功仅表示该轮正常返回。独立实验作业可能仍在运行，必须另外提供作业句柄和结果位置。

## 5. 执行与适配器

沿用现有 provider 封装，逐步拆为小适配器，至少声明访问方式、原生续接能力及受支持参数，并实现请求准备、启动、结果解析。取消和后台状态尽量共用已有 worker。

首先支持 Claude Code、Codex CLI 和现有 Gemini API。Claude/Codex 的 exec 都是首批目标，但各自的执行配置验证通过前不声明 exec 能力；请求未支持能力时直接报告原因。新增提供方修改适配器和能力注册，不增加一个任意加载代码的插件平台。

Claude 与 Codex 的 headless 模式保留各自工具循环。主控不逐条遥控 shell，也不将每个内部工具调用翻译成统一 API。

执行配置必须经过对应版本核实。默认不绕过原生权限；原生能力不足以落实任务边界时，使用已有受限环境或明确报不支持。工作区隔离不等于权限沙箱。项目说明、领域 skill 与可执行 hooks/MCP 配置分别处理，避免为加载说明就开启所有启动行为。

[Claude 官方程序化调用文档](https://code.claude.com/docs/en/headless)确认 `-p` 可保留工具循环和会话续接，但 `--bare` 会改变 OAuth 使用方式，且原生 `--bg` 不能与 `-p` 混用。因此保持现有账号渠道与后台 worker，不为精简启动而引入这些模式。

本机 `codex exec --help` 与 `codex exec resume --help` 已核实非交互执行、JSON 输出、指定工作目录和按 ID 恢复的入口；这不代替实施后的实际兼容验证。

### 目录与文件

主控用已有 Git/文件工具准备工作区：Git 并行任务用 worktree，文档和实验用独立输出目录；`ai-collab` 不自动创建、合并、清理工作区。

确需修改原目录时，在同一执行主机内使用工具内的原子提交检查，防止本工具同时执行同 realpath 或父子目录冲突任务。`jobs --workspace` 使用相同的主机和路径归属规则。不约束工具外的手工操作，不建设锁服务。已有并发上限、输出上限和超时继续保留。

长实验沿用现有作业系统或后台进程，返回句柄后单独查询。取消 ai-collab 不等于取消所有外部实验；失联先查状态，不能自动重跑。

## 6. 配方：四份，五个简短部分

| 配方 | 用途 |
| --- | --- |
| `review.md` | 对代码、方案、论文或结果获得独立第二意见 |
| `plan-execute.md` | 分析者形成建议，执行型 CLI 落地并反馈；包括实验 |
| `research.md` | 对照资料、探索方向、寻找反例和缺失证据 |
| `writing.md` | 根据材料起草、改写和交叉检查；包括论文与业务文档 |

每份包含：适用、材料、分工、交付、收尾。通常只读取最相关的一份；确有跨阶段需求再加载另一份，不机械限制为只能一份。

完整示例：

```markdown
# 独立复核
适用：需要第二意见时。
材料：待审成果、原始依据、目标与约束；先不提供主控结论。
分工：协作者独立判断，指出具体问题与证据。
讨论：主控补充缺失材料，针对影响结果的分歧继续追问。
交付：结论、问题位置、建议、尚不能判断的部分。
收尾：主控核对影响交付的问题，采纳或说明保留意见。
边界：建议执行的检查不能写成已经执行。
领域细节：按任务补充已有领域 skill 中相关要点。
```

配方不固定模型、提供方、轮次数或命令串，不负责授权；既有任务要求优先。简单问答直接调用，无需选配方。

## 7. 网页、远程与主控接手

- CLI 和薄 MCP 调用同一份核心函数，不各自保存状态。
- MCP 复用已有 LabContext/Router 的可达性与鉴权；文件解析仍留在原模块。协作模块暴露白名单操作和目录，不接收任意 shell。
- `run/reply/status/result/cancel/jobs` 映射为结构化工具；等待保持短时、有上限。终端用户不需要新增常驻服务。
- `--host` 仅引用已配置的 SSH 主机。远端使用固定入口，从 stdin 接收 JSON；提示、路径和模型参数不拼入远端 shell 字符串。
- job 与原生会话留在执行主机，返回可定位主机的 job 引用。后续命令自动路由；已有本地 job ID 保持可用。
- 跨主机传递材料必须显式读取或传输，带来源。远端的文件路径不是本机可读文件。

主控接手为人工明确交接：停止旧主控继续分派，读取相关 jobs 与短交接摘要。摘要只含目标、已完成、正在运行、关键文件、下一步；无需复制原生对话或自动主控选举。

## 8. 程序与主控的分工

| 程序落实 | 主控判断 |
| --- | --- |
| 名字和模型绑定、参数校验 | 谁适合承担当前子任务 |
| 范围/能力匹配和续接兼容 | 提供哪些材料、是否补证 |
| 原子会话占用、执行冲突检查 | 哪些工作适合并行 |
| 有限后台调用、状态、取消、错误 | 是否采纳、是否需要实际复核 |
| 文件与主机来源记录 | 何时停止讨论、怎样向用户交付 |

## 9. 实施顺序与核对

1. 补齐 Codex 适配、原生及 API `reply`、真实 cwd 和明确的 exec 配置；保持旧只读行为。
2. 将 skill 中主控与提供方的固定假设移除，加入四份按需配方。
3. 加入固定 SSH 入口与薄 MCP 映射，复用已有部署。

只核对必要功能：真实两轮续接、同会话并发拒绝、目录正确、只读不升级、执行结果落在约定位置、后台结果可取回、错误可解释、不同主控能继续工作。模型请求仅在实施验证时实际开展，不以新基准或研究实验作为上线前提。

## 10. 原设计阶段的依据与讨论记录

主控检查了现有 CLI、worker、提供方代码，本机命令帮助和官方文档；Claude Code Opus 5.5 读取同一仓库并提出接口建议，随后进行针对性复核。本次只修改设计文档，不安装 skill、不开放执行权限。

本轮共两次调用，提供方报告模型为 `claude-opus-5-5`。采纳最终复核中的 cwd 行为变更说明、reply 前置条件和同主机路径冲突规则。原生命令入口已由主控查看帮助，完整执行配置与续接效果仍须实施时验证，未将本次讨论描述为功能测试。

- [Claude Skills 文档](https://code.claude.com/docs/en/skills)：共享入口与按需资源的宿主支持参考，实际安装按宿主验证。
- [Claude 程序化调用](https://code.claude.com/docs/en/headless)：原生工具与会话能力、启动配置和后台参数差异。
- [CLI Agent Orchestrator](https://github.com/awslabs/cli-agent-orchestrator)：原生 CLI 委派的工程参考，不作为首版必须引入的依赖。
- [ARIS](https://github.com/wanshuiyin/Auto-claude-code-research-in-sleep)与[Aider](https://aider.chat/2024/09/26/architect.html)：沿用前轮已核实的轻量配方、独立复核及分析/执行分工思路。
